# Development installation and setup

**Not a published release.** Only install from a source tree or locally packed tarball you have reviewed; supported publication channels will be npm/pi.dev and GitHub Releases after the [separate release checklist](release-checklist.md). Initial target: Blender 5.2+ Linux x64 or Windows x64; see [compatibility](compatibility.md) for unqualified GUI and CI gaps. The Blender bridge is GPL-3.0-only; Pi-side resources are MIT, with both source and notices in the package.

1. Install Node.js >=22.19 and a verified pnpm 12.6.0 (the repository's tested development installer; verify its integrity before use). From this checkout, use `pnpm install --frozen-lockfile --ignore-scripts` for development, then `npm run validate`. Do **not** substitute `npm ci` or allow lifecycle scripts. Test builds are isolated from network and user Blender configuration where possible. Cross-platform validation currently has [known failures](security-validation.md).
2. Build local archives with `npm run release:build`: `dist/release/blender_pi-<version>.zip` and `dist/release/scetrov-blender-pi-<version>.tgz`. This runs offline, verifies bridge metadata, includes source/licenses, and does not publish or install. Repeat and compare hashes; validate the ZIP with Blender 5.2.2 `--background --factory-startup --command extension validate <zip>`. Use a throwaway Blender user configuration for testing.
3. After reviewing the package, [Pi package installation](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md) accepts `pi install ./` from the checkout; a local source is referenced rather than copied. A future published release can use a **version-pinned** `pi install npm:@scetrov/blender-pi@<version>` after independent npm verification. `pi list` shows packages; `pi remove <source>` removes the Pi declaration. Pi loading alone does not install Blender files, launch Blender or grant trust. Review local project trust before allowing project packages to load.
4. In interactive Pi, run `/blender-setup`. It checks release metadata and source digests, describes the destination, and asks for explicit approval before copying the Blender extension. In non-interactive Pi it prints instructions **without installing**. Automatic replacement is limited to Pi-owned destinations; never overwrite an unmanaged add-on. Alternatively install the verified ZIP manually using Blender's Extensions installation UI. Enable the add-on in Blender yourself, then explicitly select **Start Bridge** in the 3D View sidebar. Do not open network firewall ports.
5. Read the short-lived code in Blender's panel. Use `/blender-pair submit <pairing-id> <code> [inspection|full]`, inspect the displayed client name, working directory, trust and expiry in Blender, then select Allow or Deny. `/blender-pair poll <pairing-id>` checks completion on the same connection. The code is **not** in discovery. Inspection trust cannot execute arbitrary Python; full trust is Run Script-equivalent. Use `/blender-diagnostics`, `/blender-trust`, and `/blender-version` for status or compatibility failures. Commands that need UI approval cannot manufacture it in print mode.
6. Stop the bridge or select **Revoke Session** in Blender after use. To uninstall, revoke and stop first; remove the Pi package with `pi remove <source>`, then disable and remove the Blender extension using Blender's UI or remove the reviewed Pi-owned installation from Blender's user extensions directory. This does **not** delete artist `.blend` files, separate checkpoints or user-modified artifacts; review [recovery](recovery.md) before deleting recovery files. Re-pair after restarting Blender.

Only locally isolated development and headless tests have exercised these instructions; public registry install, gallery discovery, physical UI review and Windows GPU capture are **not yet release-verified**. See [secure use](secure-use.md), [pairing](pairing.md), [threat model](threat-model.md), and [release process](release-process.md).
