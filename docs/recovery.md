# Undo, checkpoints, and recovery (Blender 5.2+)

## What to do after an operation

1. **Stop and inspect the receipt.** A failed operation may have changed the scene. `undoAvailable` describes whether the Blender operator produced an undo entry; it does not mean the failure was rolled back. If the connection disappeared, do not repeat the operation: re-pair with full trust, query its exact operation ID and idempotency key, and inspect the live scene. If the result is unknown, inspect and decide anew before submitting different work.
2. **For recent scene edits, try Blender's ordinary Edit → Undo first.** Check the current file and undo history before undoing; the Pi entry uses the `Pi: <summary>` label. Undo acts on the artist's *current* history, not a transaction owned by Pi. Manual edits since the operation may be undone too. Inspect the scene after undo. An operation can be marked **failed** even when its wrapper returned `FINISHED` to preserve an undo entry for a partial edit. An absent undo entry or an external side effect cannot be fixed by Blender undo.
3. **For a high-risk change or unreliable undo, use a checkpoint.** Save any current work you want to keep to a separate file first. In the Blender Pi 3D View sidebar, find a checkpoint for the currently open original scene, choose **Restore**, read the operation, source and checkpoint paths, then explicitly confirm. The dialog defaults to Cancel and warns that even unsaved changes may be lost. If the source scene differs, return to the original scene before trying again. The checkpoint is preserved; restoring opens the checkpoint *as the active file*. Use Blender's Save As to choose a new working filename rather than accidentally treating the recovery copy as the original.
4. **Check the result and external dependencies.** A completed restore record means Blender's file-load handler observed the checkpoint open. A pending record after interruption is uncertain, not success. Check object state, texture paths and cache locations. A `.blend` snapshot does not reverse exports, overwritten files, network activity, installed add-ons, subprocesses or external simulation caches. Recover those separately from your own backups or system records. If in doubt, stop rather than retrying a destructive action.

Only the five most recent **verified** checkpoints for the current source appear in the sidebar; an older checkpoint may remain on disk and can be opened manually after checking its source and safety. Recovery files are stored alongside saved source scenes or in Blender's user config `blender-pi/recovery` directory for unsaved scenes; ownership sidecars and last restore outcomes are stored in the latter directory. The sidebar restore is a **local Blender action**, not a remote Pi tool yet. Full-trust Python is Run Script-equivalent, not sandboxed: risk detection and external-effect approval are advisory pre-execution checks, not enforcement of every actual effect. Routine full-trust Python needs no blanket uncertainty approval.

## Selected prototype

Use `bpy.ops.wm.save_as_mainfile(filepath=absolute_checkpoint_path, copy=True)` on Blender's main thread, **outside** the user operation's undo transaction. In a Blender 5.2.2 LTS headless probe (`tests/prototypes/checkpoint_blender.py`), `copy=True` wrote readable files while preserving `bpy.data.filepath` for both an unsaved scene (`""`) and an already-saved scene. Production verification checks the save result, a regular non-symlink `.blend` file, Blender header, bounded size, SHA-256 digest and matching source metadata before execution; this does not prove every saved file will reopen. Separate isolated integration tests reopen checkpoints and check scene metadata and dependencies before the mechanism is considered supported. The operator's `FINISHED` return alone is insufficient. If save, file validation, metadata creation, or dependency checks fail, block the elevated-risk mutation. Do not use ordinary Blender undo or `bpy.ops.ed.undo_push()` as the checkpoint mechanism.

**Saved scenes:** store checkpoint `.blend` files **adjacent to the active `.blend`**, with a reserved `.blender-pi-<random-operation-id>.blend` basename. The probe showed that saving to another directory leaves a `//texture.png` reference unchanged, but reopening resolves it relative to the **checkpoint's directory**, not the original scene directory. Reopening a same-directory checkpoint resolves the existing relative asset path correctly. If the source directory is not writable, do not silently fall back to a different directory: block elevated-risk execution and suggest saving in a writable location. Moving the original asset later still breaks that relative reference.

**Unsaved scenes:** `copy=True` leaves the scene unsaved but has no stable source directory. Store an unsaved-scene checkpoint under a user-scoped recovery directory. If any `//`-relative external dependencies exist, the checkpoint cannot guarantee equivalent resolution when reopened: require the artist to save the scene to a suitable location first or resolve/pack those dependencies through a separately approved workflow. Do not promise recovery of unresolved paths. UI must explain that restoring the checkpoint opens a saved copy rather than restoring the original unsaved file identity.

**Metadata and verification:** `bridge/checkpoints.py` now creates random owner-scoped names, refuses an existing destination, and records source path or unsaved state, source/session generation, operation ID, Blender version, timestamp, size and SHA-256 in a private sidecar. Verification checks a regular non-symlink file, size, SHA-256 and Blender header or Blender 5.2 Zstandard-compressed signature; the compressed signature alone does **not** prove a valid `.blend`. A separate Blender 5.2.2 process successfully reopened an integration-test checkpoint and verified pre-mutation scene state. Sidecars live in Blender's user-scoped recovery directory with owner-only permissions. The Blender Pi sidebar lists up to five verified checkpoints for the current source scene and opens a cancel-default confirmation dialog before local restore. It shows the source scene, operation ID, checkpoint path, unsaved-work warning, and external-file limitation. Restore refuses a different active source or changed checkpoint, records a pending outcome before `open_mainfile`, then records completed only after Blender's file-load handler observes the checkpoint as the active file. A failed load records failure where possible; an interrupted pending record is **not** proof of completion. Restoring an unsaved scene opens a saved checkpoint rather than restoring its unsaved identity. The checkpoint is not deleted. Remote `checkpoint.restore` remains unavailable until the authenticated request workflow is integrated.

**Retention implementation:** `CheckpointStore` defaults to keeping up to 10 bridge-owned checkpoints per source scene for 7 days, with bounds configurable in the Blender add-on preferences (the wire execution path reads these preferences). Do not remove the most recent recovery checkpoint for an unresolved/failed operation, nor any file without matching ownership metadata. Avoid silently purging files when disk space is low; block risky execution if a verified checkpoint cannot be retained. Disk consumption is scene-size-dependent and not bounded by count alone; the implementation must report usage and allow cleanup by explicit artist action.

**Recovery limits:** Blender checkpoints are snapshots of `.blend` data, not external filesystem transactions. The probe changed a separate asset file and a file in a Blender cloth modifier's external point-cache directory after checkpoint creation; reopening the adjacent `.blend` retained the cache path and read the **modified** external file, not the earlier bytes. The same limit applies to external simulation caches, rendered outputs, exports, linked assets, add-on writes, and network/process effects. Packing an image into the `.blend` can change that particular dependency's recovery scope, but the bridge will not silently pack, duplicate, or rewrite assets. This probe exercised an external cloth point-cache path and a placeholder file, not a baked simulation; real baked-cache restoration still requires separate integration tests. Never promise restoration of external cache contents.

**Implementation boundary:** The full-trust wire path now supplies an owner-scoped `CheckpointStore` rooted in Blender's user configuration directory. Declared/detected high-risk scene operations fail closed if saving or verification fails; normal trusted code does not require a checkpoint. Wire outcome lookup reports terminal state and a schema-validated receipt including declared/effective risk, trust, timing, undo availability (also for partial failures), checkpoint descriptor, warnings, artifacts, truncated output and safe errors. The receipt caps encoded data at 60 KiB; oversized results, warnings, effects and artifact lists may be truncated with `truncated: true`, never treated as proof of safe recovery. The 8 GiB checkpoint descriptor limit does not authorize Pi to load that many bytes into model context. Local artist-confirmed restoration is available in the sidebar; remote restore and fuller artist-facing recovery controls remain future tasks. Cleanup skips unknown, symlinked, changed, newest and failed-operation checkpoint records and never deletes arbitrary user files. Production verification checks signatures and digest, not a complete parse of compressed Blender contents; recovery may still fail despite a digest match.

**Prototype evidence:** verified against the official `blender-5.2.2-linux-x64.tar.xz` archive (SHA-256 `84098912789dc450e95697c4184fb8a90acbe5111c2ba4aede3fecb57806a168`) under an isolated, network-disabled process. Separate GUI Xvfb tests exercise Blender undo and risk policy, and a headless restore test exercises file loading after simulated dialog confirmation. These are not evidence for Windows, physical artist confirmation, linked library paths, baked simulation caches, or every failure mode.
