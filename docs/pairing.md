# Pairing and trust (partial implementation)

The artist explicitly starts a loopback-only listener in Blender. Pi can discover its endpoint through a user-scoped descriptor with no credential. A short-lived one-time code, a displayed requester identity and explicit Blender-side approval establish either inspection trust or full Run Script-equivalent trust in the bridge; Pi-side connection management is not yet implemented. **Inspection is not available before completed pairing.** Credentials remain in process memory and are revoked on stop, replacement or explicit artist action; this does not guarantee memory erasure. Pairing alone will not approve a particular external effect or uncertain code execution; see [risk policy](risk-policy.md).

Discovery descriptors are now published only while a listener is running. On Linux they live in `~/.local/state/blender-pi/discovery/` (directory mode 0700, files mode 0600); on Windows they live beneath `%LOCALAPPDATA%\\blender-pi\\discovery\\` and rely on the user's profile ACL. Each JSON descriptor names a literal-loopback address, ephemeral port, random public bridge ID, bridge/Blender versions, and owning PID—**never a credential or pairing code**. Publication uses a private temporary file and atomic replacement; normal stop removes the owned descriptor, and subsequent starts remove only descriptors whose owning process is provably dead. A crash can leave a stale descriptor; clients must verify the endpoint and bridge identity on connection rather than trusting the descriptor. The local panel now displays a 10-character, 50-bit random pairing challenge with a random 128-bit identifier. It expires after 180 seconds, allows at most five incorrect attempts spaced at least two seconds apart, and is invalidated on stop, restart, or successful approval. The public hello response supplies the pending pairing ID and expiry (it may temporarily omit them until bridge startup finishes); the code remains only in Blender's UI. A correct entry reserves it for one pending request. The transport now forwards schema-valid pairing requests to Blender's main thread; invalid codes are denied before any UI action. The 3D View sidebar shows the pending client and requested trust, with an explicit review dialog and denial control. The dialog displays the client's name, package version, complete escaped working directory, trust and expiry; full trust warns of unsandboxed Run Script-equivalent Python, file/credential access, network access and process launch. Dismissal, denial, expiry and disconnect cannot issue a credential. Approval now creates a 256-bit random in-memory credential; only `pair.status` on the **same connection** may receive it, once, after approval. Until approval, that connection sees pending status. Blender's Revoke Session control clears credentials, invalidates the old challenge, and displays a fresh code; disconnect and bridge stop also invalidate the session. A subsequent approval replaces the prior credential. The bridge exposes distinct unpaired, pending, inspection, and full trust states. Its method-specific trust map mirrors the versioned protocol contract; the child rejects unpaired or inspection-only execution before queueing, and the parent independently checks connection identity, trust and credentials before any future privileged dispatch. Credential comparison uses constant-time comparison. **Scene control and Pi-side session handling are still not implemented**, so this is not yet a usable agent integration. The [threat model](threat-model.md) describes what pairing cannot protect against, including compromise of the artist's OS account. Pairing limits and protocol schemas have component and headless Blender tests; the package still lacks Pi-side connection management and scene tools, so do not treat this document as end-user setup instructions.
