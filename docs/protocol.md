# Protocol contract draft (version 1.0)

The planned wire contract uses four-byte unsigned big-endian length framing around UTF-8 JSON-RPC 2.0 objects over literal loopback TCP. Each frame contains **one** JSON object. JSON-RPC `id` identifies a transport request; a distinct opaque `operationId` identifies accepted work that may outlive it. Empty payloads, invalid UTF-8/JSON, duplicate JSON object keys, invalid envelopes and excessive lengths are rejected before dispatch. Initial hard frame cap: 1 MiB per peer; negotiation may lower it, never raise it. Never allocate memory for a declared length above the negotiated limit. The frame limit does not authorize unbounded nested JSON values, queue growth or log output.

## Pre-pairing boundary

The only unauthenticated methods will be bounded `bridge.hello`, `pair.request` and `pair.status` for handshake/pairing. These return no live scene, active filename, inspection output, image capture or user-scoped diagnostics. Discovery contains an endpoint and public bridge identity/version, not a secret. The unauthenticated `bridge.hello` response optionally includes the current public `pairingId` and `pairingExpiresAt` while a challenge is available; the pairing **code** appears only in Blender's UI. If the challenge has not reached the transport child yet, these fields are absent and Pi must retry hello before requesting pairing. Neither the ID nor the code grants trust. An approved session credential is delivered only on the original live connection that submitted the code, after Blender UI approval; pending pairing is invalidated on connection loss. `pair.status` on another connection never returns a credential, even with a known pairing ID. A replaced connection must re-pair. **All scene inspection, capture, and contextual diagnostics require approved inspection- or full-trust pairing.** Arbitrary Python, mutation and recovery methods require full trust plus applicable per-operation approval. Authorization occurs before Blender main-thread scheduling; pairing code submission alone does not grant inspection.

## Versioning and namespace

Wire version `1.0`: `MAJOR.MINOR`. A different major is incompatible and fails closed with a bounded diagnostic; the negotiated minor is the minimum mutually supported minor. New optional methods or fields require an advertised capability and a minor-version increment. Do not silently accept unknown fields in security-sensitive requests. Unknown capabilities are ignored only if explicitly optional; missing mandatory capabilities prevent ready state. Pi package, bridge and Blender versions are reported separately and never substituted for protocol compatibility. The method namespace is `bridge.*` (hello/status/diagnostics), `pair.*` (request/status/revoke; approve/deny are Blender-local UI actions, never remote methods), `scene.*` (inspect/capture), `operation.*` (execute/status/outcome/cancel), `checkpoint.*` (list/restore) and `event.*` (operation state/progress/log/warning/artifact/trust). Only the bridge owns approval and scene mutation.

## Stable enums and errors

- Trust states: `unpaired`, `pending`, `inspection`, `full`. `inspection` grants only bridge-owned read-only methods; `full` permits trusted Python and controlled mutation.
- Operation states: `queued`, `active`, `cancellation_requested`, `completed`, `failed`, `cancelled`, `outcome_unknown`. Cancellation separately records `requested_by_caller`, `received_by_bridge`, `observed_by_execution`; no earlier state implies a later one. Tracked jobs have an owning operation and `registered`, `running`, `completed`, `failed`, `cancelled` terminal status; a launch returning does not complete its operation.
- Risk levels: `low`, `moderate`, `high`, `external_effect`, `unknown`. External effects may coexist with high-risk scene checkpoint requirements; unknown effects alone do not mandate a checkpoint or approval. Effective risk never downgrades declared or known risk.
- Artifact roles: `image`, `report`, `checkpoint`, `export`, `log`. Descriptors carry opaque ID, canonical path, media type, byte size and SHA-256, not inline large content.
- Stable error codes: `INVALID_FRAME`, `INVALID_JSON`, `INVALID_REQUEST`, `INVALID_PARAMS`, `METHOD_NOT_FOUND`, `UNSUPPORTED_VERSION`, `MISSING_CAPABILITY`, `PAIRING_REQUIRED`, `PAIRING_DENIED`, `PAIRING_EXPIRED`, `RATE_LIMITED`, `UNAUTHORIZED`, `STALE_PRECONDITION`, `IDEMPOTENCY_CONFLICT`, `OUTCOME_UNKNOWN`, `QUEUE_FULL`, `APPROVAL_DENIED`, `CHECKPOINT_FAILED`, `CANCELLED`, `SERIALIZATION_FAILED`, `EXECUTION_FAILED`, `ARTIFACT_INVALID`, `BRIDGE_UNAVAILABLE`, `INTERNAL_ERROR`. Each error includes a safe bounded message and correlation ID; no codes, session credentials, sensitive paths or raw tracebacks leak to unpaired peers. JSON-RPC reserved numeric errors remain in the JSON-RPC `code` field, while the stable machine-readable string lives in `data.code`.

Mutation requests require validated source, artist-readable summary/effects/risk, idempotency key and inspection-derived file/session generation plus relevant target/mode/selection preconditions. The bridge rechecks them on its main thread just before execution and after any approval delay. The current bridge revokes its pairing session at file-load start, rejects old-session queued requests, clears inspection cursors and any installed dispatcher, detaches tracked-render callbacks before the replacement file is observed, increments file generation after replacement and re-establishes its single persistent timer/registration owner. A tracked render interrupted by file load remains failed/interrupted rather than successful. Basic risk-gated mutation transport is implemented; tracked job integration and inspection cursors are tracked separately in 6.13b and 4.7b. Idempotency keys bind to authenticated session and request content within a bounded ledger; conflicting content is rejected. After an ambiguous disconnect Pi does **not** auto-resubmit: it re-pairs and looks up the retained outcome with full trust or reports `OUTCOME_UNKNOWN` and requests re-inspection/explicit decision. Disconnect cancels queued work and signals active work; the active operation may still finish. Mutation notifications preserve per-operation order; ordering between independent operations or connections is not guaranteed. Receiving progress or cancellation does not yield Blender's event loop.

## Wire limits and schemas

- Byte format: `[uint32_be byte_length][UTF-8 JSON-RPC object]`; each frame has a nonzero payload of at most **1,048,576 bytes**. A peer can negotiate a smaller limit (minimum 1,024 bytes); a larger advertisement is invalid. Framing decoders accept at most **65,536 input bytes** and **128 completed frames** per `feed` call; callers must segment larger socket reads. A bad length, truncated EOF, invalid UTF-8 or malformed/duplicate-key JSON closes the owning connection without resynchronization. Text length is validated by Unicode code point, not UTF-8 byte count; bounds in schema also apply.
- `protocol/schemas/v1.json` defines envelopes, enums, request/result/event payloads and stable error data. `methods-v1.json` binds each request method to its `params` definition and its response `result` definition through `x-results`; `events-v1.json` binds notifications. Validate the envelope **and** method/event schema before dispatch. Match response `id` to the pending method before validating its result. Unknown required method parameters and unauthorized methods fail closed. Implementations use only the schema subset exercised by the shared fixtures and must reject unsupported schema keywords before adoption, not silently ignore new constraints.
- Stable errors: JSON-RPC reserved negative numeric codes for parse/request/method/params failures, and the exact project numeric mapping in `protocol/fixtures/schema-v1.json` for bridge outcomes. Every `error.data` includes stable string code and correlation ID. Messages/details are bounded and redacted; never echo a credential, pairing code or traceback to an unpaired peer. Schema-valid text is not proof of redaction; outbound runtime checks use current in-memory secrets.
- The current bridge requires `framingV1` and advertises `framingV1`, `preconditionsV1`, `idempotencyV1`, `notificationsV1` and `cancellationV1` when requested during `bridge.hello`. `pairingV1` is not yet advertised for the complete Pi client path. Capture and tracked jobs must not be inferred from these capabilities. Notifications and cancellation are optional and are only active when explicitly negotiated. A client must call `bridge.hello` successfully on each connection before pairing or authenticated requests. Unknown optional capabilities are excluded from the intersection; missing mandatory capabilities and major mismatch return bounded errors with corrective guidance. The negotiated minor and smaller frame maximum govern the connection. `bridgeVersion` comes from the installed bridge manifest; `packageVersion` in the response echoes the caller's declared package version, not an independently attested installation. Blender version comes from the running Blender process. No automatic schema fallback or mutation replay occurs. The Pi `BridgeSession` discovers loopback descriptors on demand, keeps one hello-negotiated connection, drops in-memory credentials on disconnect, and reconciles a retained mutation only with `operation.outcome` after a fresh full-trust pairing. A restart, lookup failure, or missing re-pair is `outcome_unknown` and requires inspection plus an explicit new decision; it never resubmits `operation.execute`. Package load still does not open that session. Pi tools are registered with TypeBox schemas imported from `@earendil-works/pi-ai` so they share the host TypeBox copy. Mutation, cancel, checkpoint, and restore tools stay inactive until full trust; loading the extension does not connect.
- Controller transport foundation: the child services only one loopback connection at a time, requiring successful hello on each. The current connection is bounded to **180 seconds from accept** and **4,096 requests**; unauthenticated idle connections time out after five seconds. On disconnect its credentials are discarded in the child and the parent revokes trust. An admitted operation ID is tracked by the child before it sends the acceptance response, so a disconnect can create an empty cancellation marker even if main-thread execution has not yet reported active state. Fresh full-trust reconciliation requires both exact operation ID and idempotency key; original-session key lookup is not available to a newly paired session. Wire cancellation is independently acknowledged by the I/O child when `cancellationV1` is negotiated; execution observation remains separate.
- Bounded mutation outcome ledger: the bridge holds at most **256 entries** with **one hour** retention from acceptance in the current bridge lifetime. Active/queued entries are not silently evicted; once terminal, expired entries are removed on the next ledger access. Capacity exhaustion fails closed with `QUEUE_FULL`. Request content is represented only by a canonical SHA-256 digest; records contain no source code or raw credential. Duplicates within the original authenticated session return the existing operation ID; changed content returns `IDEMPOTENCY_CONFLICT`. Disconnect does not erase records, but bridge stop/restart does. Wire mutation admission and exact-ID/key reconciliation of bounded receipts are available to full-trust callers. Expiry/restart must be treated as `OUTCOME_UNKNOWN`, never as permission to auto-retry. A receipt may remain separately as artist recovery information without authorizing retry.

## Request methods (v1)

| Method | Params / successful result schema | Minimum trust | Notes |
| --- | --- | --- | --- |
| `bridge.hello` | `helloRequest` / `handshake` | unpaired | Public versions/capabilities only. |
| `pair.request`, `pair.status` | `pairRequest`, `pairStatusRequest` / `pairStatus` | unpaired, pending | Code entry is not approval; credential only on original approved connection. |
| `pair.revoke` | `authOnly` / `acknowledgement` | inspection | Blender UI can revoke independently. |
| `bridge.status`, `bridge.diagnostics` | `authOnly` / `diagnostics` | inspection | No user-context diagnostics pre-pairing. |
| `scene.preconditions` | `authOnly` / `preconditions` | inspection | Implemented: live main-thread file/session generation and active object, mode, exact selection snapshot. Object IDs use Blender session UIDs; reload invalidates the file generation. Full-trust execution now requires these values as scoped preconditions. |

| `scene.inspect` | `inspectionRequest` / `inspection` | inspection | Implemented live main-thread Blender/file/scene, mode, selection, objects, collections, materials, cameras, render settings and counts. A response contains at most `pageSize` datablock summaries. `nextCursor` is an opaque single-use token containing no scene data; a changed scene or file generation invalidates it. Oversized scenes also get one bounded JSON report artifact when report storage has capacity. A page is never presented as the whole scene unless `summary.complete` is true. Use `bridge.diagnostics` for bridge health. |
| `scene.capture` | `captureRequest` / `artifact` | inspection | Implemented. Workbench and rendered captures require a camera and write a PNG artifact with scene, mode, camera, frame, engine, actual dimensions and timestamp. Viewport capture requires an open 3D view and returns the same metadata. Missing context returns `BRIDGE_UNAVAILABLE` with a reason and action; no image is fabricated. Pi-side `readVerifiedArtifact` validates the allowed session directory (or an explicitly approved checkpoint recovery directory), regular-file type, role-specific byte cap, exact size and SHA-256 before returning those bytes. `attachVerifiedImage` builds a PNG image block only from that buffer. Pi tool registration remains pending in section 9; descriptors alone must never be exposed as verified image content. |
| `operation.execute` | `execution` / `acceptedOperation` | full | Preconditions, approval and checkpoint gates run before code. |
| `operation.status`, `operation.jobStatus` | `operationQuery` / `operationStatus`, `job` | inspection | Planned; currently fail closed rather than waiting on main-thread work. The tracked render announces its job in an operation-state notification, and final status is in its receipt. |
| `operation.outcome` | `outcomeLookup` / `outcome` | full | Fresh pairing on connection replacement; no automatic resubmit. |
| `operation.cancel` | `operationQuery` / `operationStatus` | full | Receipt of request is not observation by active execution. |
| `checkpoint.list`, `checkpoint.restore` | `authOnly`, `restoreRequest` / `checkpointList`, `acceptedOperation` | full | Restore still requires artist-side confirmation. |

Full-trust `operation.execute` admits one mutation at a time, keyed by the validated request and session. The accepted ID is returned before execution; the next Blender timer unit offers one-time approval for declared/detected destructive external effects and waits for Blender UI approval. Once granted, main-thread execution revalidates scoped scene preconditions, creates and verifies a checkpoint for declared/detected high-risk scene work, and revalidates again inside a dynamically registered `REGISTER`/`UNDO` operator. The actual code runs with `bpy`, `mathutils` and a bounded `bridge` binding in a fresh namespace. The approval callback used inside this operator is only a final internal boundary: remote admission always uses the real Blender UI gate; absence of detected hazards is not a safety proof. Arbitrary Python is not sandboxed.

Supported interactive renders may use `bridge.launch_render()` from trusted execution. The adapter registers the owning operation before `INVOKE_DEFAULT`; returning from the launching script does **not** settle the ledger, emit a terminal notification, release the single mutation slot or finalize artifact descriptors. The slot persists until the adapter observes Blender's terminal render callback and no render job remains. A disconnect requests cooperative cancellation but may still yield a completed render. File-load interruption produces a failed receipt with explicitly uncertain external effects; extension stop clears retained outcomes rather than claiming termination. Unregistered asynchronous work launched through arbitrary Python is outside managed lifecycle and recovery guarantees. Artifact descriptors registered by scripts are deferred with the receipt, but file validation/consumption uses the Pi-side artifact verifier when wired into Pi tools in section 9; produced-file verification remains the caller's responsibility.

The I/O child advertises `framingV1`, `preconditionsV1`, `idempotencyV1`, `notificationsV1` and `cancellationV1` when requested. `operation.outcome` requires **both** the original operation ID and idempotency key, plus fresh full-trust pairing after connection replacement. It returns retained operation state and a bounded schema-valid receipt when a terminal outcome has settled. A mismatch, expired record or bridge restart yields `OUTCOME_UNKNOWN`, never retry permission. Disconnect cancels queued work; active work gets an independent cooperative marker and may still finish. With negotiated `notificationsV1`, the child forwards schema-validated, operation-ordered progress, state, cancellation and terminal receipt notifications while a connection is live; loss or backpressure does not discard the retained outcome. With `cancellationV1`, `operation.cancel` writes an independent cancellation marker and replies `received_by_bridge`, never `observed_by_execution`. A caller's local request is not a bridge acknowledgement. While a mutation is queued/active, this initial child refuses synchronous metadata and duplicate execute requests with `BRIDGE_UNAVAILABLE` instead of waiting for Blender's blocked main thread; this keeps the child able to receive cancellation. A negative response is not mutation acceptance; an ambiguous/lost response still requires reconciliation. During non-cooperative/native work the I/O child may receive a cancellation before Blender can observe it, or process scheduling may delay even child receipt. Disconnect cancels queued work and signals active work without forcing termination. The child continues rejecting capture, restore and other unimplemented mutations.

Notifications `event.operationState`, `.progress`, `.log`, `.warning`, `.artifact`, `.cancellation`, `.completed`, `.failed`, and `.trust` are specified in `events-v1.json`. Every operation-scoped notification carries an operation ID (and sequence where applicable). No method exposes remote `pair.approve` or `pair.deny`; those are artist-only Blender UI actions.

## Lifecycle and ordering

```text
Artist explicitly starts bridge → process-isolated I/O binds loopback
  → Pi discovers public endpoint → bridge.hello (fail closed on incompatible major)
  → pair.request(code, client, trust) → pending, still untrusted
  → Blender artist approves/denies → credential only on original live connection
  → authenticated scene.inspect (file/session generation)
  → full-trust operation.execute (idempotency key + scoped preconditions)
  → queued → [Blender effect approval] → main-thread revalidation/checkpoint → active
  → ordered live events when negotiated → retained terminal receipt
  → disconnect: cancel queued, signal active; re-pair to query retained outcome
  → revoke/stop: close child/socket, invalidate credential; restart requires new pairing
```

No inter-operation global notification ordering is promised beyond deterministic mutation queue order. A request ID can finish with an accepted-operation response while later notifications/receipt use the operation ID. A lost acceptance or completion response is ambiguous: after fresh pairing, query the retained ledger; if missing or expired, inspect and make a new explicit decision. File load invalidates inspection cursors and queued mutations. Active non-yielding Python can delay Blender UI and cancellation observation even if the I/O child acknowledges a caller request. Tracked asynchronous jobs hold their operation's mutation slot until terminal state.

The fixtures in `protocol/fixtures/` cover schema shape. A real Blender 5.2.2 smoke test under a test-only external watchdog exercises full-trust wire admission, checkpoint/approval gates, progress/terminal events, cooperative cancellation, disconnect and fresh-pair outcome lookup. A separate controller **process** confirms the bridge receives cancellation during finite native `math.factorial` work that holds Blender's Python GIL: caller-local intent precedes bridge acknowledgement, and unobserved cancellation does not turn completion into cancellation. The watchdog may kill only the isolated test process group on timeout, never a user's Blender operation. A separate Xvfb GUI test under an external watchdog verifies that a wire-launched tracked render holds its mutation slot, refuses overlap, and sends a final job receipt only after adapter termination. Artifact directory/byte verification and general job-status tooling remain pending.
