# Initial execution risk and approval policy

Full-trust pairing authorizes ordinary Blender Python with Run Script-equivalent user permissions. **Blender does not sandbox Python.** The policy is a limited pre-execution safety aid against obvious hazards, not a guarantee against undeclared or indirect file, process, network or add-on effects. It cannot mediate each call inside arbitrary trusted Python.

| Effective risk | Example | Gate before execution |
| --- | --- | --- |
| Low | Bounded undoable scene change | Full trust, relevant live-state preconditions, supported undo wrapper. No repeated approval. |
| Moderate | Larger known undoable scene change | Low gates plus receipt and undo-limit warning. |
| High | Declared or clearly detected destructive in-scene replacement | Verified checkpoint; failure blocks execution. |
| External-effect | Declared or clearly detected broad filesystem deletion, user-file overwrite, process launch, network disclosure or installation change | Explicit artist approval naming the effect and known target (or honestly identifying an uncertain target). A checkpoint is mandatory only when high-risk scene effects also apply; it cannot undo external effects. |
| Unknown | Agent declares unclear effects, or specific hazards have uncertain scope | Report uncertainty; unknown effects **alone** do not trigger a mandatory checkpoint or blanket approval. An obvious destructive hazard still needs approval even if its target cannot be identified. |

Declared risk is never silently downgraded. Advisory code patterns may escalate a declared risk or flag an obvious hazard, but the absence of a match is **not** proof of safety. Do not classify all arbitrary Python as unknown simply because unrestricted code cannot be proven harmless. Full trust permits everyday Blender operations without repeated uncertainty prompts. A user can explicitly request a checkpoint for extra protection.

**Current implementation boundary:** Internal execution validates the request schema and rejects blank/control-character summaries or effect descriptions. Declared external-effect categories require an explicit nonblank target; unknown effects cannot claim a known target. These are declaration-quality checks, not proof the target is correct or permission to execute. An internal advisory risk calculator now retains declared risk, flags a small set of literal process/file/network calls and broad Blender file-reset operations, and records separate checkpoint/approval decisions. It may miss aliases, dynamic calls and indirect add-on behavior; a normal classification is not a safety verdict. The internal execution boundary now requires a verified high-risk checkpoint and a one-time Blender UI grant for each declared or clearly detected external hazard; denial, stale/changed code, revocation or expiry blocks that internal operation before its code runs. The panel displays the operation summary and known effect target or honestly labels an unknown target. This is not enforceable mediation of indirect Python effects, and **remote mutation admission and full receipts remain future tasks**: the transport still rejects `operation.execute`.

When detected or declared hazards need approval, denial/dismissal blocks code execution; main-thread preconditions are rechecked after approval. Partial failures remain failures even when the Blender operator returns `FINISHED` to preserve undo. Cooperative cancellation may be delayed during non-yielding Python. Neither checkpoints nor undo restore external files or reverse network/process effects. The artist should review full-trust requests and stop when a proposed action is suspicious.
