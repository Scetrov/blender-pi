# Architecture (pre-release implementation)

Pi loads an MIT-licensed TypeScript extension and focused skills. Blender loads a thin GPL-3.0-only add-on after the artist explicitly enables it. The add-on owns authentication, main-thread `bpy` operations, per-operation approvals, undo/checkpoints, inspection and artifact creation; a separate bundled Python child process handles loopback transport without importing `bpy`. Pi and Blender negotiate a versioned framed JSON-RPC contract. The live `.blend` remains the only scene authority; Pi re-inspects and uses operation-scoped preconditions before mutations. See [I/O gate](io-architecture.md), [protocol](protocol.md), [pairing](pairing.md), and [risk policy](risk-policy.md).

The Pi extension, process-isolated I/O bridge, pairing, main-thread mutation path, inspection, capture and recovery have component and headless Blender 5.2.2 tests. Package loading itself remains inert until a session or explicit command needs the bridge. One mutation owns the scene at a time; tracked jobs retain that slot until terminal state, while finite non-cooperative Python may leave UI status stale. Checkpoint/approval heuristics do not sandbox arbitrary Python. The [OpenSpec tasks](../openspec/changes/establish-blender-pi-package/tasks.md) and [current validation](security-validation.md) track remaining release gates; recent Linux/Windows CI failures mean this is **not** a qualified release. Licensing boundaries are documented in [licensing](licensing.md).
