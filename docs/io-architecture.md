# Blender 5.2 I/O architecture gate

**Decision: use a separate standard-library Python child process for loopback socket I/O. Do not run a persistent Python thread in Blender.** The [Blender 5.2 Python threading documentation](https://docs.blender.org/api/5.2/info_gotchas_threading.html) explicitly says persistent Python threads are unsupported, including threads that appear harmless until Cycles, Python drivers, and rendering interact. Merely avoiding `bpy` in a thread or passing a stress test does not override this guidance. The documentation recommends a separate process for independent work.

The Blender extension owns UI, pairing approval, session policy, main-thread scheduling, `bpy`, undo, checkpoints, inspection, and artifacts. `scripts/stage_bridge.py` packages MIT-licensed Python framing/validation sources and schemas alongside GPL bridge code with both license notices; the I/O child runs the staged copy with isolated Python import mode. The worker supports public `bridge.hello`, forwards validated pairing requests to Blender's main-thread policy, and returns one-time session credentials only to the original live pairing connection after approval. It rejects unauthenticated and insufficient-trust methods before queueing, forwards only a bounded allowlist of read-only authenticated methods through main-thread IPC, and validates/redacts their responses before writing to the original connection. Mutations and capture remain disabled until the idempotency, operation ownership and cancellation policy is implemented; no Blender scene-control path is operational yet. A bridge-owned child interpreter owns literal-loopback socket accept/read/write, four-byte framing, bounded validation, and transport-level authorization checks on plain messages only; it **must not import `bpy`** or expose an unauthenticated control path. Parent/child IPC uses a separate ephemeral loopback socket authenticated with a 256-bit random nonce transferred once through the child's private stdin pipe; the nonce is never put in argv or a descriptor. `bridge/ipc.py` bounds each side to 128 queued messages, 4 MiB outbound bytes and eight inbound/outbound frames per poll. Blender polls this nonblocking in-memory channel from a `bpy.app.timers` main-thread callback (50 ms scheduled interval); the I/O child has no `bpy` access. Only opaque operation IDs may be written as empty owner-private cancellation marker files in the bridge's temporary directory, allowing cooperative checks without waiting for the main-thread work queue. Pairing credentials and scene/code messages must never be serialized into these marker files. Temporary files and sockets are removed on normal stop; a process crash can leave OS-managed temporary files until cleanup, so do not claim durable erasure. Never serialize live Blender references or session credentials to disk. Blender's main thread must independently revalidate authorization, file/session generation and operation preconditions at dispatch. Start only on explicit artist action. Stop must close listener, signal child, drain/cancel queued work, revoke secrets, wait with a bounded timeout, and terminate the owned child only when necessary; termination of the transport process must never be described as cancellation of active Python running in Blender. Monitor child exit, refuse further control while unavailable, and avoid orphans on extension unload, file loads, Blender shutdown and Pi disconnect. Child crashes must fail closed.

**Feasibility evidence:** `tests/prototypes/io_feasibility_blender.py` ran under network-disabled process isolation with official Blender 5.2.2 Linux x64. It launched the bundled Blender Python interpreter as an independent child, exchanged loopback messages before and after loading a `.blend`, rendered a 32×32 Cycles CPU image while a scripted Python driver evaluated, observed the child heartbeat advance, and cooperatively shut down the child with exit code 0. This is a short **architecture smoke test, not a Blender threading safety proof** or cross-platform qualification. A further Xvfb GUI smoke test observed the registered dispatcher timer execute twice on Blender's main thread and stop cleanly; this does not establish UI responsiveness while long Python work blocks. Repeat on the supported Windows x64 baseline, physical GUI Blender, longer renders, repeated file loads and reloads, crash/disconnect/revoke paths, and shutdown races before release.

**Internal render adapter (not wire-enabled):** Blender 5.2.2 GUI testing confirms `bpy.ops.render.render('INVOKE_DEFAULT')` returns `RUNNING_MODAL` while `bpy.app.is_job_running('RENDER')` remains true. `bridge/jobs.py` registers render handlers and reserves a single owner *before* launch, blocks subsequent internal undo mutations and render launches, and releases the slot only after the job stops and a terminal signal is observed on main-thread polling. Missing terminal callbacks fail instead of implying success; disconnect/revoke records a cancellation request without forcibly stopping Blender, and file load records an interrupted outcome after the render stops. Unload drops handlers and marks the owner interrupted, never successful. This internal adapter does not admit remote renders, hold a production wire operation open, or emit final receipts/artifacts; 6.13b covers those guarantees after risk gating. Unregistered asynchronous Python/add-on work is outside managed lifecycle guarantees. [Blender 5.2 render handlers](https://docs.blender.org/api/5.2/bpy.app.handlers.html) and [`is_job_running`](https://docs.blender.org/api/5.2/bpy.app.html#bpy.app.is_job_running) inform the adapter; the actual asynchronous invoke behavior was checked in the GUI test rather than assumed from operator documentation.

**Internal staged callbacks (not wire-enabled):** `bridge/stages.py` schedules one cooperative unit of work per Blender timer tick, holds the same internal mutation slot as the render adapter, checks cancellation between units, and reports maximum step duration, maximum dispatch gap and over-budget steps. File load, disconnect and extension unload invalidate remaining stages before another callback can mutate a replacement scene. A callback that blocks beyond its declared budget cannot be preempted; neither a progress event nor a timer interval promises a UI latency bound. In an isolated Blender 5.2.2 Xvfb GUI run, three 5 ms work units allowed a separate timer to run between them, but the worst timer gap was about 3.9 seconds due to GUI/startup scheduling. Do not advertise responsive staged workflows based on this short smoke test; repeat measurements on target hardware and workload. No remote code execution or final receipts are available through this runner yet.

**Limits:** the child has its own GIL and can usually process socket traffic while Blender runs native code, but a Blender main-thread Python operation that does not yield still blocks Blender UI/timers and cannot observe cooperative cancellation until it checks its signal. Parent/child IPC and OS scheduling add latency. Pi must distinguish locally requested cancellation, child receipt, parent bridge receipt, and execution observation; do not acknowledge a state before it actually occurred. Rendering and drivers can saturate CPU; heartbeat progress does not prove UI responsiveness or safe dispatch. Stage advertised responsive work with bounded main-thread callbacks returning to the event loop; tracked asynchronous jobs keep the mutation slot until completion. Parent and child startup/shutdown are explicit and platform-specific executable discovery and process termination require integration coverage. Authenticated `bridge.status`/`bridge.diagnostics` currently return an in-memory snapshot: listener, child process, maximum IPC queue depth, dispatcher availability, protocol version, frame limit, advertised capabilities, trust and at most 16 recent errors. Child framing/validation failures are forwarded as stable error codes; the snapshot stores no request contents, pairing codes or credentials. Errors remain in Blender memory until exit (bounded ring; no disk log). Advanced panel status is visible only to the artist, while protocol diagnostics require inspection or full trust. No external downloads, third-party Python dependencies or host-network listeners are required at runtime.
