# Release process (planned, not active)

The offline packaging command `npm run release:build` produces `dist/release/blender_pi-<version>.zip` and `dist/release/scetrov-blender-pi-<version>.tgz` from the same local source. It verifies the checked-in bridge release metadata and file digest, requires matching npm and Blender manifest versions, writes a ZIP with sorted allowlisted members and fixed timestamps/modes, and invokes npm pack offline with lifecycle scripts disabled. Blender's archive includes GPL bridge source and its license plus MIT wire source and its notice. The npm tarball includes the bridge source, metadata, skills and Pi code, but no bundled host peers or runtime dependencies. `dist/` is ignored; build twice and compare SHA-256 before release, then validate the ZIP with Blender 5.2.2's `--command extension validate`. Building does not install or publish either artifact and needs only the existing Node.js, npm and system Python; it downloads nothing at runtime.

There are no published releases. `.github/workflows/release-candidate.yml` builds from a signed, verified `vMAJOR.MINOR.PATCH` tag only after the reusable Linux/Windows validation matrix, compares two offline builds, checks matching component versions, produces SHA-256 checksums, SPDX 2.3 file inventories and compatibility metadata, validates the Blender ZIP, and requests GitHub build-provenance attestations for each output. Candidate artifacts are retained as CI artifacts, not published merely by building them. The publish job is disabled unless the operator explicitly sets `NPM_TRUSTED_PUBLISHER_READY=true` **after** bootstrapping the first npm version and verifying that the trusted publisher is bound to this repository, workflow filename (`release-candidate.yml`) and `release` environment. The job rechecks the protected environment and artifact attestations, creates an unpublished GitHub draft, publishes the already-verified npm tarball via OIDC, then publishes the draft; neither publication is atomic across registries. If npm succeeds but the final GitHub edit fails, halt and reconcile the draft rather than republishing the npm version. This workflow has not yet run on a signed release tag; do not treat its existence as successful publication. The GitHub `release` environment was configured and read back with required reviewer `RichardSlater` (user ID 630786), self-review prevention, custom deployment policies and exactly one `v*` **tag** policy; this is a repository setting, not proof that a future workflow will enforce tag signatures or exact artifact versions. The operator selected GitHub's signed-tag verification plus local GPG verification using public keys currently listed for the approved `Scetrov` account. `scripts/verify_release_tag.py` rejects unverified/unsigned tag objects, mismatched source and manifest versions, and keys outside that account's GitHub listing. It deliberately supports GPG tags only; access to GitHub's key listing is part of this trust boundary. The gate is not yet wired into a publishing workflow or exercised on an actual signed release tag. Before publication: complete real Blender 5.2 integration on Linux x64 and Windows x64; verify packed Pi and GPL Blender artifacts include their source/license notices; run protocol, security, dependency, license and package checks; produce checksums, SBOMs and provenance from the same signed source tag; and obtain maintainer release approval in a protected environment. Use trusted npm publishing where available, not a long-lived registry token. **Initial-publication blocker:** `@scetrov/blender-pi` returned HTTP 404 from the npm registry on 2026-09-28. npm's current trusted-publisher configuration requires an existing package, so the first package version cannot be published via OIDC alone ([npm CLI issue #8544](https://github.com/npm/cli/issues/8544)). Decision: after signed release approval, an operator manually publishes the verified first tarball with interactive npm authentication, outside CI and without a CI publish token; then configures and verifies the trusted publisher for subsequent automated releases. Release automation must fail closed for the initial version and whenever the OIDC binding is absent. The separate release checklist records the operator's actual actions. Never silently add a long-lived publish secret or claim the trusted publisher is already configured. Refer to [compatibility](compatibility.md), [licensing](licensing.md), [security](../SECURITY.md), and the [release template](../.github/RELEASE_TEMPLATE.md).

Archive the completed OpenSpec implementation change **before the final signed conventional commit and PR**. Publication approval and verification of public npm installation, pi.dev discovery, GitHub release artifacts, checksums, SBOMs and provenance belong to the **[separate release checklist](release-checklist.md)**; archiving implementation does not imply publication succeeded. First release has no prior stable version to roll back to: the matrix now builds both archives and runs `scripts/verify_release_install.py` for Blender ZIP and npm tarball installation/removal in disposable private profiles on each target OS. Check CI results on the actual tagged revision; the local Linux 5.2.2/Node 24.21.0 run passed with development version `0.0.0`, which is not a signed release candidate. Verify revocation and checkpoint recovery separately; if a prior candidate becomes available, verify it before claiming a downgrade path. Do not publish while private vulnerability reporting or required hosted settings are unverified.
