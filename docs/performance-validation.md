# Bounded performance checks

`tests/test_performance.py` exercises 4,000 small frames, the 128-item IPC queue in deliberate eight-frame service batches, and 600 progress attempts while reserving terminal event capacity. `tests/prototypes/performance_blender.py` exercises 1,000 idle polls, paginates a 384-object scene at 32 objects per page, bounds each response below the 1 MiB frame limit, and verifies a 32×24 workbench artifact stays below the 16 MiB image cap. Both run offline; CI also requires the real Blender success marker.

On the operator's isolated local Linux Blender 5.2.2 fixture, framing took about 0.009 s, the IPC batch 0.002 s, progress 0.030 s for 250 accepted events, 1,000 idle polls below displayed millisecond precision, and large-scene inspection 0.111 s over 13 pages. These are **measurements, not a UI latency guarantee**. Generous regression ceilings (10 s for unit loops; 30 s for scene paging) avoid treating noisy hosted-runner timings as precise performance claims. Actual responsiveness of non-yielding Python, render jobs, GUI redraw and GPU capture requires separate display-capable testing; stage timers are checked by `tests/prototypes/stages_blender.py` only where a GUI is available.
