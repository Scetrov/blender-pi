# Headless Pi-to-Blender lifecycle coverage

`tests/prototypes/pi_headless_blender.py` starts a real Blender 5.2 bridge, then launches `tests/integration/pi_client_headless.mjs` in a **separate Node process** using the real Pi `BridgeSession` and framed transport. A watchdog must require both `BLENDER_PI_HEADLESS_OK` and a zero exit status: Blender may exit zero after a script assertion fails. Pairing codes travel only over the test child's stdin, never via discovery or logs. Artist approval and restore confirmation are simulated only in the Blender-side test process; production still requires an explicit UI action.

The test covers loopback discovery, initial and post-restore full-trust pairing, live inspection and preconditions, accepted low/high-risk Python changes, ordered progress/completion summaries, a verified workbench PNG artifact, a high-risk checkpoint and authenticated listing, queued restore with no automatic load, simulated artist confirmation, recorded restore outcome, file replacement, re-pairing, revocation and shutdown. The low-risk receipt asserts the bridge reported an undo step. Separate GUI-oriented `tests/prototypes/execution_boundary_blender.py` exercises actual Blender undo when a valid UI context is available.

**Not proven headlessly:** actual interactive `bpy.ops.ed.undo()` in the Pi-to-Blender lifecycle (background Blender rejects it without a UI context), a physical 3D viewport screenshot, the visual appearance of the pairing/restore dialogs, GPU-backed capture, or Windows GPU capture. Linux hosted CI uses Xvfb with software Mesa and requires a digest-verified workbench PNG. Hosted Windows Blender 5.2.2 crashes in WGL initialization (`EXCEPTION_ACCESS_VIOLATION`) during Workbench capture on the standard VM; CI sets `BLENDER_PI_CI_SKIP_GPU_CAPTURE=1` only for Windows to run the remaining real-Blender checks. On a Windows machine with a working graphics context, leave this flag unset: the capture assertion remains mandatory. Windows capture requires a dedicated capable runner before release, and this exclusion is not evidence of passing Windows visual validation.

The CI matrix invokes `scripts/run_blender_smoke.py`, which checks success markers for both the inspection and Pi-to-Blender headless cases after acquiring the exact pinned official Blender archive. The latest [validation run 36478655413](https://github.com/Scetrov/blender-pi/actions/runs/36478655413) failed the Linux client with `BRIDGE_UNAVAILABLE` and a Windows unit test; do not count earlier successful CI runs as current release qualification. Local validation uses network-isolated Bubblewrap with the project as the sole writable host mount and read-only mounts of the operator-approved Blender 5.2.2 and Node 24.21.0 fixtures; no display, home, credential path, or host network is exposed.
