# Threat model: pairing and local access

## Boundary and authority

Pi and Blender run as the same OS user. The bridge binds to literal `127.0.0.1`; discovery publishes its endpoint, public bridge ID, versions and PID but **no bearer credential or code**. Starting the listener is an artist action. The boundary pairing enforces is between an unpaired local caller and access explicitly approved by the artist in Blender. Even bridge-owned scene inspection requires completed inspection or full pairing. An unpaired caller receives only bounded public hello/pairing responses, not scene data or privileged diagnostics. Inspection trust does not authorize arbitrary Python; full trust is Blender Run Script-equivalent authority, **not a sandbox**. Pairing is not approval for a particular external effect or uncertain execution request.

The Blender main thread reserves one pending request after validating the short-lived code; the Blender approval dialog displays the requesting name, package version, working directory, trust and expiry. Denial, dialog dismissal, disconnect and expiry cannot grant trust. Approval issues a fresh random memory-only credential on the requesting connection, retrievable through `pair.status` once. Both the process-isolated I/O child and Blender's main-thread dispatcher check authenticated method access. Revocation, replacement, stop and expiration invalidate the credential; a restarted bridge requires new pairing. Credentials are not intentionally written to disk or diagnostic records, but Python cannot guarantee memory erasure, and process dumps or swap may contain secrets.

## Local adversaries and mitigations

| Threat | Current control | Residual risk |
| --- | --- | --- |
| Another local caller guesses the pairing code or replays a claim | Random 50-bit code, 128-bit pairing ID, 180-second lifetime, at most five wrong attempts spaced two seconds apart, one pending claimant, one-time approval | A caller who sees the artist's display or intercepts loopback traffic can race for the pending request; the artist must verify the displayed identity. Claimed metadata is untrusted. |
| Caller forges a request or reuses an old credential | Random 256-bit credential, session/connection binding, method trust checks before queueing and on main-thread dispatch, constant-time credential comparison | Local TCP is not encrypted or mutually authenticated. A process with same-user socket/process access may interfere with or observe traffic; these checks are not a defense against account compromise. |
| Stale or malicious discovery file | Owner-scoped descriptor, bounded JSON, atomic publication, removal on orderly stop and of provably dead owners; endpoint must be verified with a live handshake | Crash can leave a stale descriptor; PID reuse and a same-user writer can spoof files. Discovery is a locator, not a trust root. Windows profile ACL enforcement is not yet integration-verified. |
| Approval spoofing, accidental elevated trust or replay | Explicit Blender approval showing trust and requester details; Run Script warning for full trust; denial/dismissal and one-time retrieval tested in headless Blender | Client name, version and directory are self-asserted. Headless tests exercise dialog text and callbacks, **not** physical GUI rendering or human comprehension. |
| Malformed frames, resource exhaustion or connection flooding | Length/schema validation before Blender dispatch, bounded frame/queues/errors, attempt limits, single controlling connection | Local callers may still deny service or freeze Blender through fully trusted non-cooperative Python; progress/cancellation checks do not forcibly interrupt it. |
| Secret leakage in responses or diagnostics | Credentials and codes excluded from discovery and pending records; bounded stable error codes, redacted/validated responses and a bounded in-memory diagnostic ring | Arbitrary full-trust code can read environment/process secrets and emit them; redaction is not a general data-loss-prevention boundary. |

The implementation admits paired inspection/capture, risk-gated full-trust mutation and Pi-side session management; these features are tested in component and headless Blender runs, not yet release-qualified. Conformance and unit tests plus headless Blender pairing tests cover denial, dismissal callback, expiration/replay, attempt limits, restart, revocation, concurrent pending requests, stale descriptors and diagnostic redaction. They do not establish a GUI or Windows security claim.

## Explicitly outside the security boundary

A process that has compromised the artist's OS account can read scene files, control Blender's UI, inspect or alter Pi/Blender process memory, watch the code on screen, replace same-user discovery material, or invoke Blender directly. Loopback binding, file permissions, pairing and in-memory credentials **do not protect the artist against that attacker**. Nor does this design protect against a malicious `.blend` file, installed add-on, full-trust generated Python, or a prompt that persuades the artist to approve harmful code. Trusted Python may write or exfiltrate files, use network libraries or launch processes with the user's privileges. Pre-execution risk declarations, approvals and checkpoints provide visibility and recovery, not enforceable per-effect mediation.

Protocol, path-manipulation, file-load, cancellation, idempotency, approval, and no-project-telemetry cases have tests; they do not eliminate prompt injection, same-user compromise, dependency or release compromise, or untested indirect effects.
